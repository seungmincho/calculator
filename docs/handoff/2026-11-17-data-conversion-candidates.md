# 데이터 변환 후속 후보 조사

2026-11-17 KST. 23~25차 다음 기존 도구 개선 후보다. 분석 근거는 현재 코드이며 최근 방문 통계나 사용자 선호도를 새로 측정한 것은 아니다. 별도 경로/서버/패키지는 필요하지 않다.

## JSON/CSV — 붙여 넣은 표의 내용을 보존하기

`src/components/JsonCsvConverter.tsx`는 CSV를 먼저 줄 단위로 나눈 뒤 각 줄을 파싱한다. 따라서 따옴표 안의 줄바꿈이 새 행이 되고, 탭 구분은 따옴표를 처리하지 않는다. `trim()`은 셀 앞뒤 공백을 지우고 `Number()`는 `00123` 같은 식별자의 앞자리 0을 잃게 한다. 테이블 미리보기에도 별도 파서가 있어 내려받은 내용과 일치하지 않을 수 있다. `header=false`인데 미리보기는 첫 행을 헤더로 취급하며 전체 열 통계는 첫 객체의 키만 센다.

사용자가 얻는 변화는 여러 줄 주소/메모가 포함된 표를 변환하고, 전화번호·상품 코드·긴 식별자를 문자열로 보존하며, 결과 표와 반출 파일의 동일성을 확인하는 것이다. CSV→JSON에서 기본 문자열 보존과 명시적인 숫자 변환 옵션을 제공한다. 기존 JSON 평탄화/배열 옵션·CSV 구분자·헤더 유무·페이지네이션은 유지한다.

추가로 코드의 EUC-KR 선택값은 현재 읽기/다운로드에 사용되지 않는다. 이를 파일 읽기 인코딩으로 명시하고 실제 읽기에 적용하며, 출력은 UTF-8임을 분명히 해야 한다. 현재 100MB 업로드 허용만으로 큰 문서 처리 성능을 보장할 수 없으므로 입력/행/셀/깊이 상한과 실제 경계 검증이 필요하다.

CSV의 공백 보존, 따옴표 안 줄바꿈과 두 겹 따옴표는 [RFC 4180 §2](https://www.rfc-editor.org/info/rfc4180/#section-2)를 참고한다. 쉼표 외 구분자와 LF/CR 입력 허용은 이 도구의 명시적 확장이지 모든 CSV 방언 호환 주장으로 삼지 않는다.

## Base64 — URL용 변형과 올바른 파일 읽기

`src/components/Base64Converter.tsx`의 파일 업로드는 인코딩/디코딩 모드 모두 `readAsDataURL`을 쓴다. 디코딩하려고 Base64 텍스트 파일을 올리면 파일 내용 대신 새 data URL이 입력된다. 인코딩 파일 업로드 뒤 변환 버튼을 다시 누르면 data URL 문자열을 재인코딩한다. 이미지 판단도 `data:image/` 접두사만 사용하며 출력 문자열과 안내 문장을 같은 상태에 보관한다. 모드/입력 전환 중 늦은 파일 읽기 및 복사 응답을 무효화하지 않는다.

사용자가 얻는 변화는 표준 Base64와 Base64URL을 명시적으로 고르고, 텍스트/파일 입력의 목적을 혼동하지 않고 변환·복사·다운로드하는 것이다. UTF-8 한글/이모지·바이너리 파일을 구분하고, 결과가 텍스트가 아닐 때 임의로 깨진 문자를 성공 표시하지 않는다. 기존 파일→data URL과 이미지 미리보기는 별도 명확한 결과로 유지한다.

[RFC 4648 §5](https://www.rfc-editor.org/info/rfc4648/#section-5)는 URL/파일명용 변형의 `-`와 `_` 및 문맥에 따른 패딩 생략을 설명한다. 도구는 선택한 형식과 패딩 정책을 표시하고 잘못된 알파벳·패딩·길이를 거부한다. data URL을 읽을 때는 별도 wrapper 규칙과 실제 바이트 검증을 적용한다.
