## 1. 텍스트 변환: 단계 순서 이동과 작업 되돌리기 — 우선순위 P1 가설

- **문제:** 공백 정리→중복 제거처럼 순서가 중요한 변환을 만들다가 앞 단계 하나를 옮기려면 삭제하고 다시 추가해야 한다. 정규식·치환문·접두/접미를 다시 입력해야 할 수 있고, 중간 단계 삭제나 전체 초기화를 취소할 방법도 없다.
- **이미 있는 것:** 12종 케이스 변환, 여러 변환 단계의 순차 실행, 정규식/단순 치환, 접두·접미, 목록 출력, 단계 개별 삭제, 마지막 단계 제거, 전체 초기화, 안전한 단계 종류의 URL 복원이 있다. 원문 입력은 결과와 분리되어 있다. 따라서 단순 ‘undo 버튼 추가’나 ‘여러 단계 변환’은 중복이다.
- **최소 범위:** 기존 단계에 위/아래 이동을 제공한다. 단계 추가·이동·삭제·전체 초기화를 한정된 메모리 이력으로 되돌리기/다시 실행한다. 원문 입력과 찾기/치환 작성 중 폼은 자동 교체하지 않는다. 단계 객체의 치환 설정·flags·shuffle seed를 그대로 보존하고 경계 이동/no-op은 이력을 만들지 않는다. 새 편집 뒤 redo를 버리고, 외부 URL 복원은 새 이력의 시작으로 삼는다. 저장 기능이나 새 변환 규칙은 추가하지 않는다.
- **위험:** URL은 원문·치환 문자열을 의도적으로 제외한다. undo를 URL 문자열로 재구성하면 민감한 단계를 잃거나 shuffle 순서가 바뀐다. 원래 `runPipeline`의 실패 단계 건너뛰기 정책과 `REGEX_MAX`를 바꾸지 않고 정규식의 실행 안전성이 강화됐다고 주장하지 않는다. `copy`의 거짓 성공 경로는 함께 고칠 경우 범위를 명시할 별도 작은 보완이며 이번 후보의 핵심은 단계 편집이다.
- **검증:** trim/dedupe 순서를 바꾸었을 때 다른 결과, 동일 단계 여러 개 중 정확한 위치 이동, replace·affix·seed 보존, 삭제/초기화 undo→redo, undo 뒤 새 작업의 redo 폐기, URL 진입과 자기 URL 동기화의 이력 분리, 원문 입력 불변, 한글/빈 줄, 키보드·320px·44px 이동 버튼. 기존 `check-text-convert.ts`는 계산 규칙 회귀용으로 재사용한다.
- **파일 근거:** `src/components/TextConverter.tsx:50` 원문/steps 별도 상태, `:63` URL 복원, `:69` 단일 `update`, `:77` 순차 계산, `:214` shuffle seed 생성, `:272` 현재 undo는 `steps.slice(0, -1)`, `:294` 중간 단계 제거. `src/utils/textConvert.ts:87` 단계 데이터, `:151` 정규식 제한, `:189` 순차 적용/실패 처리, `:199` 문자열을 제외하는 URL 인코딩.

## 2. QR 스캐너: 여러 이미지의 순차 처리와 파일별 결과 — 우선순위 P2 가설

- **문제:** QR이 있는 여러 캡처를 확인할 때 이미지 선택과 결과 복사를 파일마다 반복한다. 현재 한 이미지에 여러 QR이 감지되어도 첫 결과만 사용하며, 이미지 읽기/디코딩 실패와 QR 미검출이 충분히 구분되지 않는다.
- **이미 있는 것:** 카메라 스캔, 이미지 업로드/드롭, 내용 유형 분류, 결과 복사, 링크의 명시적 열기, 내용 기준 중복을 제거한 최근 기록 20개가 있다. 9차의 여러 QR **생성**·PNG ZIP은 다른 방향의 기능이다.
- **최소 범위:** 같은 `/qr-scanner/` 이미지 탭에서 제한된 여러 파일을 명시 선택하고 하나씩 처리한다. 파일 이름별 대기/처리/성공/미검출/읽기 실패를 보여 주고 취소·실패 항목 재시도를 제공한다. 아래 디코더 추가 조사에 따라 **파일당 처음 읽힌 QR 1개**로 범위를 정하는 안을 권한다. 여러 코드의 전체 검출을 약속하지 않고 QR 하나씩 잘라 입력하도록 안내한다. 결과 목록의 중복 내용은 파일 식별과 함께 유지하고, 복사·선택 결과 TXT 반출은 사용자가 누를 때만 실행한다. 일괄 원본 이미지·결과는 자동 저장하지 않고 기존 단일 스캔/카메라 기록 정책은 보존한다.
- **위험:** `BarcodeDetector` 존재 검사만으로 지원 형식이나 생성/실행 성공을 보장할 수 없다. 현재 엔진으로 가능한 환경을 먼저 확인하며 새 디코더 패키지는 별도 결정이다. 입력 수·파일 크기·디코딩 픽셀 상한을 정하고 순차 처리해 메모리를 제한한다. 취소/새 선택/탭 이동/unmount 이후 늦은 FileReader·Image·detect 완료가 새 목록을 덮지 않게 한다. Wi-Fi/연락처 등 원문을 자동으로 열거나 서버에 보내지 않는다. 기존 `qrScanHistory`는 무검증 JSON 읽기이므로 재사용 범위에서 손상 데이터 보존을 점검한다. 현재 복사 거부/`execCommand(false)` 성공 표시도 새 목록 복사로 복제하지 않는다.
- **검증:** 한글·중복 파일명·동일 내용의 서로 다른 이미지, 정상/미검출/손상/과대 파일이 섞인 선택, 한 이미지에 여러 QR일 때 단일 반환 및 한계 고지, 파일 완료 역순/취소/재시도/새 선택, 미지원 및 생성/감지 오류, 원문과 실제 TXT 일치, 복사 거부/수동 선택, 320px·긴 내용·카메라 종료와 기존 기록 회귀. 실제 QR 픽셀 디코딩과 mock 오류 검사를 구분한다. 기존 생성기에서 만든 QR을 실제 입력 fixture로 쓸 수 있다.
- **파일 근거:** `src/components/QrScanner.tsx:54` 기록 무검증 읽기, `:65` API 존재 검사, `:91` 내용 중복 제거/20개 기록, `:192` 단일 파일 처리, `:202`/`:207` 비동기 이미지 콜백, `:219`/`:221` 감지 목록 중 첫 값 사용, `:236`/`:255` 업로드/드롭 `files[0]`, `:261` 복사, `:278` 예외 뒤에도 성공 상태, `:460` 단일 파일 입력. 제품에 대체 디코더가 없고 `scripts/check-repeat-batch9-browser.mjs:320`의 디코더는 검증용이다.

코드만 읽어 흐름 부재와 위험 경로를 확인했다. 브라우저 재현·성능 측정·전체 타입 검사·제품/번역 변경은 실행하지 않았다. 구체 상한과 UI 계약은 후보를 실제 큐에 넣을 때 확정한다.

## QR 모바일 대응 추가 조사 — 같은 날, 설치/구현 미실행

**현재 자산:** `scripts/check-repeat-batch9-browser.mjs:10`의 실제 디코더는 `https://cdn.jsdelivr.net/npm/jsqr@1.4.0/dist/jsQR.js`다. `:321`에서 테스트 페이지에 script를 주입하고 `:179`에서 canvas RGBA를 `window.jsQR(...)`에 넘긴다. 제품 자산이 아니다. 현재 `package.json`과 `package-lock.json`을 모두 검색했으며 `jsqr`/ZXing은 없고 `qrcode`·`jsbarcode`만 있다. npm 설치·의존성 파일 변경·코드 다운로드는 하지 않았다.

**공식 근거:**

- jsQR 공식 저장소의 현재 `package.json`은 1.4.0, TypeScript 선언 포함, Apache-2.0을 명시한다. 런타임 dependencies는 선언되어 있지 않다. [공식 package.json](https://github.com/cozmo/jsQR/blob/master/package.json)
- API는 RGBA와 폭/높이를 받아 단일 `QRCode | null`을 반환한다. 실제 `scan`은 후보 중 처음 디코딩된 결과에서 반환한다. 전체 QR 목록이나 화면 좌상단 우선 순서를 보장하는 API가 아니다. [공식 README](https://github.com/cozmo/jsQR#usage), [공식 구현](https://github.com/cozmo/jsQR/blob/master/src/index.ts)
- Chrome 공식 문서는 생성자 존재만 확인하는 것으로 충분하지 않으며 `getSupportedFormats()`의 `qr_code`를 확인하고 기본 감지 API를 점진적 최적화로 사용할 것을 안내한다. 해당 문서의 오래된 OS 표를 2026년 전체 모바일 지원표로 인용하지 않는다. [Chrome 개발자 문서](https://developer.chrome.com/docs/capabilities/shape-detection#feature_detection)
- 조회 시점 MDN의 공식 호환성 데이터 저장소는 Android Chrome 83부터, Firefox 미지원, Safari/iOS Safari는 17부터 feature flag 조건으로 기록한다. iOS에서 기본 제공된다고 표현할 근거가 없으며 브라우저 이름만으로 성공을 단정하지 않는다. [MDN Browser Compatibility Data](https://github.com/mdn/browser-compat-data/blob/main/api/BarcodeDetector.json)
- WICG 현행 초안은 API가 SecureContext의 Window/Worker에 노출될 수 있고, 감지의 Promise와 `getSupportedFormats()`를 정의한다. 브라우저 구현 여부와 실제 성공은 별개다. [API 초안](https://wicg.github.io/shape-detection-api/#barcode-detection-api)

**추천 1안: 네이티브 우선 + 자체 번들 jsQR Worker fallback.** 21차 계약에서 외부 디코더 1개 도입을 선택한다면 `jsqr@1.4.0`을 npm에 고정해 lockfile로 관리하고, 필요한 때만 자체 Worker 청크를 로드한다. 9차 검사의 런타임 CDN 주입을 제품에 복제하지 않는다. 라이선스 고지와 실측 번들 크기는 도입 시 확인할 항목이며 현재 확인하지 않은 크기/성능을 주장하지 않는다. 이는 초기의 ‘새 패키지 도입을 전제로 하지 않음’에서 **QR 모바일 지원을 위해 별도 결정이 필요한 조건**이다. 의존성을 추가하지 않는 계약을 유지한다면 QR 후보는 네이티브 지원 환경 한정으로 축소하고 모바일 포괄 지원을 약속하지 않아야 한다.

1. 사용자 이미지 선택 뒤 파일/픽셀 한도를 확인한다. `BarcodeDetector` 존재·`getSupportedFormats` 성공·`qr_code` 포함·생성 성공을 확인해 네이티브 경로를 선택한다.
2. 네이티브 미지원/실패/시간 초과/미검출이면 유효한 RGBA를 얻을 수 있는 경우에 한해 jsQR로 한 번 시도한다. 두 경로의 결과는 공통 요청 세대에 속한다. 늦은 native 완료는 fallback/취소/새 선택 결과를 덮지 않는다. 이미지 자체가 깨져 픽셀을 읽지 못한 경우는 읽기 오류로 끝낸다.
3. jsQR은 플랫폼 코드를 포함하지 않는 순수 픽셀 디코더이므로 Worker에서 동기 계산을 수행하도록 감쌀 수 있다는 설계 판단이다. 파일은 순차 처리하고 픽셀 버퍼를 전송·해제한다. 취소/시간 초과 시 Worker를 종료한다. 모듈 로딩 실패·Worker 미지원·읽기 오류와 정상 미검출을 구분하고, 실패를 ‘QR 없음’으로 성공 처리하지 않는다. 이번 개선은 이미지 탭에 먼저 적용하고 카메라 fallback/프레임 처리 개편은 범위에 넣지 않는다.
4. 두 엔진 모두 **파일당 읽힌 첫 QR 한 개**를 제품 계약으로 삼는다. ‘첫’은 엔진이 반환한 첫 성공이며 위치 순서가 아니다. native에서 여러 값이 반환되면 여러 코드가 감지되었으나 한 개만 표시한다고 알릴 수 있다. jsQR의 단일 반환으로 이미지에 QR이 한 개뿐이라고 판정하지 않는다. 공통 안내는 ‘한 이미지에 QR이 여러 개면 하나씩 잘라서 올려 주세요’로 둔다.

**도입 검증 기준:** 실제 QR 픽셀에서 네이티브 경로와 강제 fallback의 한글/URL/Wi-Fi 결과 일치, BarcodeDetector 없음·형식 미지원·생성 throw·detect reject/timeout·모듈 로딩 실패, 취소/재시도와 버퍼 해제, 한 이미지 여러 QR의 비보장 안내를 검사한다. iOS Safari·Android Chrome 실기기 확인 전에는 지원 확대의 구현만으로 실기기 검증 완료라고 기록하지 않는다. 자동 링크 열기·원문 업로드는 추가하지 않는다.
