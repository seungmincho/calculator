# 회의록 → 칸반 연결, 멀티 에이전트 검증 결과

2026-11-16, KST. 사용자 요청으로 작업 에이전트 4명과 통합 담당 1명이 병렬 구현했다. 계약 작성 21:53 → 신규 통합 브라우저 검사·타입/린트 완료 및 화면 확인 22:05. 대조 실행이 없으므로 단독 작업 대비 속도 배수는 산출하지 않았다. 한도·쿠폰 잔액을 읽거나 초기화 항목을 사용하지 않았다.

현재 로컬 개발 서버 3039에 적용되어 있다. 빌드·배포·커밋은 실행하지 않았다.

## 사용 흐름

1. `/meeting-minutes/` 상단 **할 일을 칸반으로 보내기**에서 필요한 일을 선택한다. 담당자·기한·상태를 확인하고, 잘못된 항목은 원본 회의록에서 수정한다.
2. 선택한 일을 보내면 원본 회의록을 기기에 저장하고 새 칸반 탭을 연다. 내용은 URL에 넣지 않는다.
3. 상태별 회의 전용 열을 추가하거나, 사용자가 지정한 기존 열에 추가한다. 기존 카드와 열을 보존한다.
4. 칸반 카드에서 담당자·기한을 편집하고, 드래그 또는 상시 표시된 열 선택으로 이동한다. 제목·설명·담당자로 검색할 수 있다.
5. 같은 회의의 같은 일을 다시 보내면 이미 있는 카드는 건너뛴다. 칸반에서 수정한 내용을 덮어쓰지 않는다. 카드를 직접 삭제한 뒤 다시 가져오는 것은 가능하다.

복사한 뒤 두 도구의 변경은 자동으로 서로 반영되지 않는다. 새 카드 우선순위는 기본값 ‘보통’이며 AI가 중요도를 판단하지 않는다. 업무가 길면 카드 제목은 줄여 보여도 설명에 전체 본문을 보존한다.

## 입력·저장 기준

- 최대 50개, 업무 하나 최대 6,000자, 업무 합계 30,000자, 회의 제목·담당자 120자. 날짜는 빈값 또는 실제 존재하는 YYYY-MM-DD.
- 새 탭의 sessionStorage에 전달한다. 최초 열기·읽기 유효 시간은 10분이고, 이미 불러온 항목을 검토하는 시간에는 제한이 없다. 적용·닫기 후 임시 데이터와 from 쿼리를 지운다.
- 이전 v1 칸반 JSON을 계속 읽고 내보낼 수 있다. 담당자와 회의 출처는 선택적 필드로 확장했다. 빈 보드도 저장된다.
- 저장에 성공한 뒤 화면 변경을 확정한다. 용량·권한 오류, 손상 데이터·미지원 버전, 다른 탭의 변경을 감지하면 기존 저장본을 보존하고 오류를 안내한다. 입력 중인 모달과 회의 가져오기 내용은 실패 시 유지한다.
- JSON 가져오기는 검증 후 교체 확인을 거친다. 큰 파일은 읽기 전에 제한한다. 카드 편집·JSON 내보내기에서 회의 출처를 유지하므로 재전달 시에도 중복을 판단할 수 있다.
- 원래 회의록에 안정적인 kanbanSourceId를 저장한다. 구형 자동저장본과 이름 붙인 저장본에 동일한 비어 있지 않은 할 일 ID 집합이 있으면 알려진 ID를 재사용하고, ID가 없는 일치 저장본을 보완한다. 텍스트 유사도로 회의를 추정하거나 서로 다른 명시적 ID를 합치지 않는다.

## 이번 병렬 작업에서 확인한 점

- 공통 API와 파일 소유권을 먼저 정해 데이터 담당과 두 UI 담당이 동시에 구현했다.
- UI 담당자가 자기 번역을 작성하고 통합 담당만 원본 JSON을 병합해 공용 파일 충돌을 피했다.
- 독립 검증자가 TTL 안내와 동작의 불일치를 발견했고, 완료된 회의록 담당자의 교차 리뷰에서 구형 저장본 중복 경계가 발견됐다. 재현 시나리오를 추가해 수정 결과까지 확인했다.
- 에이전트의 완료 보고를 합치는 것만으로 끝내지 않고, 통합된 코드로 전체 타입 검사와 브라우저 검증을 수행했다.

실제 휴대폰·Safari/Firefox·프로덕션 정적 export는 이번 검증 범위 밖이다. localStorage에는 원자적 compare-and-swap이 없어 일반적인 오래된 탭 변경은 감지하지만 완전히 동시인 쓰기를 잠금으로 직렬화하지는 못한다. 초기 병렬 구현과 통합 중 결과를 확인한 범위이며, 토큰 소모량이나 한도 사용량을 측정한 실험은 아니다.
