# 17차 독립 브라우저 검증

최종 **11/11 PASS**(음력 ICS 5개 + 수능 목표 6개), JavaScript·hydration 오류 **0건**. 마지막 검사 시각은 2026-11-17 00:51 KST(2026-11-16 15:51 UTC)다. Chrome을 닫고 통합 담당에게 전체 타입 검사 가능 시점을 알렸다.

기존 `http://127.0.0.1:3039` 서버와 격리 Chrome 한 개에서 순차 실행했다. 외부 요청·서비스 워커를 차단했고 검증용 입력만 사용했다. 16차 전체 검사를 반복하지 않았다. 제품 파일 수정·서버 재시작·빌드·배포·Git·전체 타입 검사는 이 담당이 실행하지 않았다.

실행 스크립트: [check-repeat-batch17-browser.mjs](../../../scripts/check-repeat-batch17-browser.mjs). 집계: [browser/final-results.json](browser/final-results.json). 원인 추적용 최초 실패 기록을 보존하고 최종 집계에는 사례별 가장 최근 실행을 사용했다.

## 독립 ICS 읽기

브라우저가 내려받은 실제 bytes를 제품 캘린더/날짜 유틸을 가져오지 않는 검증 파서로 읽었다. 엄격한 UTF-8 디코딩, BOM 없음, CRLF, 물리 줄 75바이트 이하, 줄 펼침, BEGIN/END 구조, 중복 속성/UID, DATE 시작·다음날 종료, UTC DTSTAMP 형식, TEXT 이스케이프 복원과 양력 반복 규칙 없음 등을 확인했다. 각 파일의 `-parsed.json`도 함께 저장했다.

날짜 표본은 기존 음력 회귀 검사의 알려진 한국 음력 날짜와 실제 화면을 대조했다. 이번 검사가 모든 음력 변환 날짜의 정확성을 새로 인증한다는 의미는 아니다. 외부 캘린더에 등록하거나 반복 가져오기 중복 처리를 검사하지 않았다.

## 발견과 수정 확인

1. **320px 연도 잘림 — 제품 수정 후 해결.** 최초 모바일 시각 확인에서 기존 날짜 3열의 연도 선택이 ‘202’까지만 보였다. 음력 담당이 모바일에서 연도를 한 행, 월/일을 다음 행에 배치했다. 해당 모바일 사례만 다시 실행해 선택 문구가 들어갈 폭을 검사하고 캡처를 직접 확인했다. 변환·연도표 복사·공유·ICS도 유지됐다.
2. **범위 사례의 초기 패널 조작 — 테스트 준비 오류.** 날짜 URL 복원이 끝나기 전에 details를 조작해 닫힌 입력을 기다렸다. 실제 연도/월 복원이 끝난 뒤 패널을 열도록 준비 순서를 고치고 첫날·마지막날·미지원 연도 사례만 재실행해 통과했다. 관련 제품 변경은 하지 않았다.

수능 목표 6개는 최초 실행에서 모두 통과했으며 추가 미해결 제품 결함은 없다.

320px는 데스크톱 Chrome 뷰포트이며 실제 모바일 기기를 대체하지 않는다. `language=en` 기능·원시 키와 신규 ko/en 구조를 확인했지만 공통 도구 레지스트리의 한국어 표시 제약으로 본문 영어 전환 완료를 주장하지 않는다.

두 탭은 실제 Chrome Web Locks/storage event를 사용했다. 저장 실패와 SHA 지연/예외는 격리 검증 컨텍스트에 주입했다. 쓰기 후 확인 불가에서는 이미 반영된 저장을 인정하며 rollback을 보장하지 않는다. 최종 서버 배포·검색 색인·외부 캘린더 등록은 이 검증 범위에 포함되지 않는다.
